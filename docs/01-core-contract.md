# 核心契约：从参考到严格复刻

## 1. 成功定义

“参考某个设计系统”默认意味着严格复刻它的设计语言，而非做一个相似版本。目标业务可以拥有完全不同的信息架构、字段、内容和流程，但只要两个元素承担相同语义角色，它们的视觉和交互实现就应来自同一套精确规范。

必须一致的范围包括：

- 字体文件、字体族、回退、字号、字重、行高、字距；
- primitive、semantic、component Token；
- 前景、背景、边框、图标、反馈色、透明度和渐变；
- 间距、尺寸、容器、栅格、密度、对齐与断点；
- 圆角、边框、阴影、模糊、层级和 overlay；
- 图标尺寸、描边、填充、对齐和影像处理；
- 组件 anatomy、变体、内容约束和所有主要状态；
- 导航、表单、列表、详情、浮层、反馈和异常模式；
- 动效时长、easing、位移、透明度和减弱动效行为；
- light/dark 主题选择、切换和每个状态的主题表现。

不能用“感觉一致”“比较像”“高级”“现代”等主观描述代替具体规则和验收。

## 2. 可变与不可变

### 允许随业务变化

- 文案和真实业务数据；
- 字段名称、字段数量和业务状态；
- 模块数量及业务流程；
- 导航信息架构；
- 用户有权替换的品牌标识与业务素材。

### 默认不可随意变化

- 同语义组件的结构和视觉参数；
- 设计 Token；
- 字体层级；
- 页面壳层和空间节奏；
- 状态反馈语法；
- 主题映射；
- 响应式行为模式。

新业务出现档案未覆盖的组件时，应先寻找现有模式的可组合方案，再请求原系统证据。只有用户明确允许推断时才能扩展，并把扩展标为 `Recommended`，不能称其为来源系统的原始规则。

## 3. 明色与暗色是平行系统

每个档案强制要求 `light` 和 `dark`：

- 共享结构不代表共享视觉值；
- 同一语义必须建立双向映射；
- 两主题证据、截图、分析、Token、CSS、组件状态和验收分别保存；
- 不以简单反色、统一亮度偏移或主观经验补全另一主题；
- 不因某个颜色“看起来也能用”而跨主题引用；
- 支持主题切换时记录触发方式、持久化、系统偏好和首屏闪烁处理；
- 缺少任一主题的来源证据时，档案不能成为 `complete`。

## 4. 精确性等级

每项关键规则应说明精确性来源：

1. `exact-source`：来自源码、设计 Token、设计稿属性或浏览器计算样式；
2. `exact-measured`：来自未缩放原图、已知 DPR/视口的可靠测量；
3. `inferred-system`：由多个证据归纳，尚需验证；
4. `recommended-extension`：为新场景补充，不是来源事实；
5. `unknown`：没有证据。

严格复刻优先使用前两级。关键规则若停留在后三类，必须进入 TODO，并阻止完整状态。

## 5. 决策优先级

同一规则有多个来源时：

1. 当前版本的可验证源码、官方 Token、设计稿属性或计算样式；
2. 多页面、多状态重复出现且环境已知的证据；
3. 单张未缩放截图的测量；
4. 归纳推断；
5. 补全建议。

冲突不能被静默抹平。记录主题、断点、浏览器、版本、状态、A/B 实验等可能原因，必要时向用户确认目标版本。

## 6. 不静默优化

严格复刻模式下，Agent 不得以“更美观”“更现代”或“更易实现”为由改变值。发现低对比度、不可见焦点、触控区域过小或动效风险时：

1. 保存并描述来源事实；
2. 记录可访问性或可用性风险；
3. 向用户说明严格复刻值与建议修正的差异；
4. 只有用户确认后才应用修正；
5. 将修正记录为显式偏差，不反写为来源事实。

## 7. 完整性承诺

“百分百复刻”是验证目标，不是无证据承诺。只有档案达到 `complete`，另一个 Agent 才能把它作为完整输入。只要存在关键未知、任一主题缺失、近似字体、未覆盖状态、未验证断点或开放 TODO，就必须明确说“当前不能保证完全一致”。
